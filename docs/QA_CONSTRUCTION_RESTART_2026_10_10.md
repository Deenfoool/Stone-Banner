# P5 — восстановление строительного плана после restart

10 октября 2026, alpha.50. Контрольный сценарий вынесен в acceptanceTest;
игровая логика не изменена. Полная приёмка 1.12/P5 остаётся открытой.

## Что проверяется

Три отдельных процесса настоящего Forge DedicatedServer 1.20.1 / 47.4.23,
Java 17.0.20, Gradle 8.8. Только новый изолированный мир
stonebanner-construction-probe (seed 11252), адрес 127.0.0.1:25577.

Коробка стандартного коттеджа заранее построена фикстурой. Осталось установить
две кровати и дверь. В зарегистрированном физическом сундуке лежат ровно два
предмета WHITE_BED (в отдельных слотах) и один OAK_DOOR. NPC получает эти предметы
через обычный контроллер стройки; телепортаций и ручной установки мебели после
начала работы нет.

1. Реальный строитель получает BUILDING-работу, берёт кровати со склада,
   устанавливает первую. Проверка ждёт WORKING и ещё три тика: в сумке остаётся
   одна кровать, в сундуке — дверь. Незавершённый план и NPC сохраняются; сервер
   штатно останавливается.
2. Загружаются тот же NPC, план и склад. Проверяются UUID, ID/владелец плана,
   origin/rotation/размеры, blueprint/fingerprint, регистрация склада и сохранённая
   кровать в сумке. Временная аренда и маршрут не восстанавливаются. Строитель
   заново получает работу, заканчивает вторую кровать и дверь.
3. После ещё одного сохранения и перезапуска план остаётся completed, вся
   геометрия мебели совпадает с blueprint, материалы не возвращаются, BUILDING
   не публикуется повторно. Наблюдение ещё 120 тиков пересекает обычную границу
   100-тикового ConstructionService.reconcile.

На каждом тике проверяется баланс: установленные предметы мебели + оставшиеся
в сундуке/сумке = 3. Две части кровати или двери стоят один предмет. Внешних
выпавших кроватей/дверей быть не должно; личные три apple сохраняются.

## Повторный запуск

После принятия Minecraft EULA в отдельном run-acceptance-construction/eula.txt:

```bash
bash scripts/verify-construction-restart.sh
```

Требуются JDK 17, Bash, GNU timeout и flock. Аргументы передаются Gradle;
в данном headless-прогоне клиентские assets не загружались (`-x downloadAssets`).
Используется общий runner с закрытым выбором сценария forestry/construction;
каждый сценарий имеет собственные папку, мир и порт. Старый мир или параллельный
запуск отклоняются до открытия логов этапов. Проверки не входят в mod JAR.

## Фактический результат

Штатные скрипты завершились с кодом 0: **три construction-процесса и три forestry-процесса**.
Строитель `87468203-c9ff-4863-9345-329a1f1fa7f0`, plan #1:
установки **1 → 3 → 3**, оставшиеся физические материалы **2 → 0 → 0**,
completed **false → true → true**. Общий runner повторно проверен старым сценарием
рубки: WORKING, затем ровно один oak_log, без повторной добычи после ещё одной загрузки.
[Машинный отчёт](qa/construction-restart-20261010.json), [выдержки логов](qa/construction-restart-20261010.log).

Отказы параллельного запуска, неизвестного сценария и повторного использования
строительного QA-мира проверены с кодом 2; level.dat существующего мира не изменился.

Обычный `test build reobfJar` завершился с кодом 0: **414 JUnit**, без падений,
ошибок и пропусков. В reobfuscated JAR нет acceptanceTest/GameTest-классов;
pack.mcmeta валиден. 149 GameTest повторно не запускались — последний checkpoint 09.10.

## Границы результата

Это достройка подготовленного коттеджа, а не строительство всего здания с нуля.
Не проверены restart с временными лесами, отмена/пауза сложного плана, внешние
blueprint-пакеты, миграция старого пользовательского мира и аварийное прерывание
посередине записи save. Ручные P0–P4 и нагрузочная P5 также остаются открытыми.
Dev-предупреждения Mojang/LAN/union не трактуются как автоматическое доказательство
игровой ошибки; полной чистоты логов этот отчёт не заявляет.
