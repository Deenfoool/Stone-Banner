# QA — 09.10.2026: восстановление рабочих заданий (P5)

Продолжение незакрытой 1.12/P5, без расширения G7 и изменения игровой логики.

## Проверенные сценарии

- `CitizenQueueGameTests.reloadedWorkerReacquiresPublishedWorkExactlyOnce`: сохранение незавершённого рабочего состояния NPC проходит через сжатый NBT и загрузку. Опубликованное задание остаётся в Job Board, исполнительная аренда/маршрут сбрасываются, приоритет работы сохраняется. Обычные серверные тики заново выбирают работу, удаляют дерево и создают ровно один физический лог; через дополнительные 20 тиков нет повторного задания или дропа. Переноска в этой сцене отключена, чтобы изолировать физическую добычу.
- `CitizenQueueGameTests.compressedReloadClearsMixedAndMovementQueues`: смешанная очередь и очередь путевых точек очищаются после сжатого NBT round-trip. Наниматель сохраняется, NPC не воспроизводит старое движение на последующих тиках.
- `CitizenJobBoardTest.legacySaveWithoutNextIdDoesNotReuseExistingJobIdentity`: старый формат без `NextId` загружается через сжатый NBT; завершённая работа не появляется снова, существующее задание сохраняется, новые ID не пересекаются с ним.
- `CitizenJobBoardTest.reloadedReservationBelongsOnlyToNewClaimant`: загрузка сбрасывает старую аренду. Прежний исполнитель не может продлить, завершить или освободить работу, которую уже получил другой NPC.

Исправлена **подготовка теста**, не игровой код: отключена переноска перед сохранением. Не считать этот отказ найденным/исправленным багом мода.

- Сборка `build/libs/stonebanner-0.1.0-alpha.49.jar` успешна. Добавлены только тесты и документация; игровое поведение этого JAR не менялось.

## Границы результата

NBT round-trip внутри GameTest не равен полноценному перезапуску dedicated-server с непустой очередью. Существующие работы должны сохраняться как мировые задания и заново приобретаться NPC; временные маршруты/боевые приказы намеренно не сериализуются. Выход игрока без выгрузки NPC и загрузка сущности — разные сценарии.

P5 остаётся открытой: ручные P0–P4, команды и права через настоящий клиент, перезапуск сервера с непустыми заданиями, миграция реально более старого пользовательского мира и нагрузочная приёмка. Прошлый dedicated smoke с копией текущего мира описан в [отчёте 08.10](QA_2026_10_08.md). Новый dedicated/client запуск в этом продолжении не выполнялся.

## P5 — устойчивость загрузки реестра заданий (09.10.2026)

- Устранено **тихое затирание разных задач с одинаковым сохранённым ID**: разные работы восстанавливаются с отдельными IDs, следующий ID не пересекается с исходными допустимыми записями.

## P5 — завершение задания только действующим исполнителем

- `CitizenJobBoard.complete` теперь удаляет задание **только** при совпадении ненулевого UUID заявителя с текущей арендой. Отмена/принудительное удаление по-прежнему выполняется через явные `remove` / `removeAt`.
- Это закрывает класс ошибок: после перезагрузки или освобождения аренды прежний NPC не должен удалять опубликованную работу, которую никто пока заново не взял.

## P5 — безопасность NBT сохранённых шахт

Ранее `ExcavationPlanData.load` молча затирал разные планы с одинаковым ID и принимал некорректные границы без проверки лимитов; это могло потерять шахту либо вызвать многократную проверку огромного объёма после загрузки. Теперь загрузчик проверяет наличие всех границ, порядок координат и `DesignationLimits`, восстанавливает отдельные ID для дубликатов без подмены последующих исходных ID, не восстанавливает план с фронтом за его границами и помечает данные изменёнными. Счётчик ID больше не переполняется при `createVertical/createTunnel`. Добавлены 3 JUnit-теста на повреждённые записи. Java17/Forge прогон на этом HEAD пока не выполнен.

## P5 — безопасное восстановление направления проходки

`ExcavationPlanData.load` теперь не подменяет неизвестный `Mode` вертикальным карьером и неизвестный `AccessMode` — автоматическими лесами/лестницами. Неправильные типы NBT для этих полей, отсутствующий `CurrentSlice/CurrentY`, нулевой либо неподходящий знак `Step` приводят к безопасному пропуску некорректной записи, а не к добыче по выдуманному маршруту. Отсутствующие поля исходного вертикального формата (`Mode`, `Step` при наличии `CurrentY`) по-прежнему восстанавливаются. Четыре JUnit-сценария добавлены; полный Gradle/Forge прогон ещё не подтверждён.
